Finding your data

Building a query

A query is just a filter — “give me the rows that match these conditions.” Some filters you can type in one line; others are complex enough that you build them visually in DataGrouper and save them to reuse. This page shows both, with the command line in MATLAB and Python side by side.

The one idea that makes it click

In DataGrouper you pick a View level (Dataset, Cell, Epoch…) and add conditions. On the command line you start from a table and narrow it with the restriction operator &. The key move is that you can restrict one table by another — which is exactly what DataGrouper’s view levels and Restrict by selection do under the hood. Because the tables share keys (see Data levels), DataJoint works out the join for you.

Python setup varies Everyone loads the schemas their own way, so the Python snippets assume the schema module is already bound to its name (sln_symphony, sln_cell…) — e.g. from your_pkg import sln_symphony or a dj.create_virtual_module(…) call. The table names (Dataset, UserParamDatasetDrugPresent…) are the same as in MATLAB, so only that first binding line changes. Note there’s no aka.* in Python — use the raw sln_* tables.

Simple filters you can write by hand

Example 1 · wildcards✓ verified

Everything recorded on one date / rig

The file_name encodes the date and rig (e.g. 101323A = 13 Oct 2023, rig A), so a LIKE with a % wildcard is all you need. In DataGrouper: View level Dataset → Add condition with attribute on file_name → IS LIKE → 101323A% → Run.

MATLAB
datasets = sln_symphony.Dataset & 'file_name LIKE "101323A%"';
datasets.count        % -> 32
Python
datasets = sln_symphony.Dataset & 'file_name LIKE "101323A%"'
len(datasets)         # -> 32

Tables: just sln_symphony.Dataset. (In MATLAB, aka.Dataset is a handy alias for the same table.)

Example 2 · filter by a tag✓ verified

Datasets where a drug was present

A tag is its own little table keyed to the dataset (see tags in DataGrouper). You filter the dataset by that table — the restrict-one-table-by-another idiom. In DataGrouper: Add condition with user param → DrugPresent → Run.

MATLAB
% any dataset with a drug recorded:
drug = sln_symphony.Dataset & ...
       (sln_symphony.UserParamDatasetDrugPresent & 'drug_present IS NOT NULL');
drug.count            % -> 275

% ...or one specific drug:
gz = sln_symphony.Dataset & ...
     (sln_symphony.UserParamDatasetDrugPresent & 'drug_present LIKE "%gabazine%"');
gz.count              % -> 24
Python
drug = (sln_symphony.Dataset
        & (sln_symphony.UserParamDatasetDrugPresent & 'drug_present IS NOT NULL'))
len(drug)             # -> 275

gz = (sln_symphony.Dataset
      & (sln_symphony.UserParamDatasetDrugPresent & 'drug_present LIKE "%gabazine%"'))
len(gz)               # -> 24

Tables: Dataset, UserParamDatasetDrugPresent (attribute drug_present).

Example 3 · combine conditions

Both at once — one rig, drug-free

Each extra & is one more AND. (In DataGrouper, stacking conditions does the same.)

MATLAB
sel = sln_symphony.Dataset & 'file_name LIKE "101323A%"' & ...
      (sln_symphony.UserParamDatasetDrugPresent & 'drug_present IS NULL');
Python
sel = (sln_symphony.Dataset & 'file_name LIKE "101323A%"'
       & (sln_symphony.UserParamDatasetDrugPresent & 'drug_present IS NULL'))

Nothing runs until you ask — add .count / len() to see the size, or fetch/export (see Exporting data). That’s the same as hitting Run in DataGrouper.

Complex filters: build once, reuse

Some filters are too tangled to type. “All ON-alpha cells” is the classic one, because a cell’s type isn’t a stored column — it’s the most recent type-assignment event, which means joining the cell to its assignment history and keeping the latest. Add a protocol and a couple of exclusions and the generated SQL runs to dozens of lines:

roughly, what DataGrouper generates
-- the part you care about:
WHERE amp_mode   = "Cell attached"
  AND protocol_name = "spots_multi_size"
  AND cell_type  = "ON alpha"
-- ...resting on ~10 joins you don't want to write by hand:
--   experiment -> retina -> cell -> eye -> animal,
--   assign_type & cell_event (latest assignment = current type),
--   and a UNION over every spots_multi_size protocol version.

So for anything beyond a simple attribute, the workflow is build it in DataGrouper, then save it:

Build it visually

View level Dataset; add a condition on cell_type (ON alpha), another for the protocol, any exclusions; Run to check the count.

Save it

Save query stores it in sln_lab.Query under a name and project — as the SQL it generated.

Reuse it anywhere

You (or a labmate) re-run it by name from QueryBrowser, or from code:

MATLAB
q = sln_lab.Query & 'query_name = "Ref_SMS_CA_ON_alpha"';
datasets = q.runAndFetch();      % runs the saved query, returns the datasets
Python
sql = (sln_lab.Query & 'query_name = "Ref_SMS_CA_ON_alpha"').fetch1('sql_query')
import datajoint as dj
rows = dj.conn().query(sql).fetchall()   # run the stored SQL on your connection
There's already a library The lab has 70+ saved queries in sln_lab.Query — Ref_SMS_CA_ON_alpha, SMS_CA_OFF_sus_alpha_clean, Ref_SMS_CA_by_cell_type, and more. Before building a new one, browse what’s there in QueryBrowser; odds are your filter, or a close starting point, already exists.
Heads up Cell type resolves to the latest assignment, so re-typing a cell changes what matches. And query_name can repeat across users — if fetch1 complains, add & 'user_name = "…"'.
Once you have a query Everything downstream is the same whether you built it by clicking or typing: count it, plot it, run an analysis on it, or export it.
